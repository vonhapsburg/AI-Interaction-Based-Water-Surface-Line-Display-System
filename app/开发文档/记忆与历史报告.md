## 二、病因三问，逐条对账

| 病因（文档原话） | 原实现 | 现在 |
|---|---|---|
| ① `/api/solve` 每次都从零解析，上一句的 b=5 没留在任何地方 | 确实如此，每次 `merge(text)` 独立 | 服务端 `STATE["slots"]` 累计；`/api/turn` 只做增量 |
| ② 送给模型的只有当前这一句，没有当前参数表 | 确实如此 | `llm.ask(text, current=state)`，SYSTEM 里带【当前已记录参数】 |
| ③ `num_ctx=2048` + 每轮新请求 = 每次新会话 | 2048，且无状态 | 提到 **4096**（多带了参数表）；但**仍不靠上下文记忆**，靠槽位表 |

第三条要特别说明：把 `num_ctx` 提到 4096 只是为了让 system 里能放下参数表，**不是**让模型靠长上下文去记住历史。文档里那句判断是对的——4B 级模型在第五轮后槽位保持能力明显下降，实测也印证了：让它自己从长对话里抽参数，第五轮就开始丢前序数值。

## 三、实现：三层各管一件事

```
用户第 N 句
   │
   ├─ parser：只抽「这一句里说到的字段」 → delta {b:6}
   │
   ├─ merge.turn(state, delta)：把 delta 并进 state，同值不重复、异值记警告
   │      state = {b:6, n:0.015, i:0.001}   ← 记忆在这里
   │
   ├─ 只有「规则一个字段都没抽到」且「还缺字段」才叫模型
   │      llm.ask(本句, current=state) → 只返回本句提到的字段，其余 -1
   │
   └─ adapter + legality + gvf_core.solve
```

关键代码（`agent/merge.py`）：

```python
def turn(text, state, use_llm=True):
    r = rule_parse(text)                       # 只看这一句
    delta = {k: v for k, v in r["slots"].items() if v not in (None, "")}
    added = _apply(state, delta, warns, "规则")  # 并进全局状态
    missing = missing_of(state)
    if use_llm and not added and missing:      # 规则没抽到才叫模型
        lr = llm.ask(text, current=state)
        added += _apply(state, lr["slots"], warns, "模型")
    ...
```

`_apply` 的规则：新字段直接写入；已有字段被改成不同值 → 覆盖并记「n 由 0.015 改为 0.02（规则）」；同值不产生噪音。

### 模型提示词里加了什么

```
【当前已记录参数】
{current}
（这份参数只用于理解「改成」「那个」「它」指的是什么，不要复制到输出里）

12. 用户说「改成」「换成」「调整到」时，只输出该字段的新值。
    你只负责「这一句话里说了什么」；没提到的字段一律 -1，历史值由程序合并，
    绝不能把下面的【当前已记录参数】抄进输出。
```

这条"不要抄"的约束很关键：不写清楚，模型看到 current 里有 `b:5` 就会在输出里也带上 `b:5`，看起来像"记得"，其实每轮都在重复确认，还会把旧值覆盖回去。

## 四、历史记录（对应顶层设计的 L1 数据层）

顶层设计写的是"SQLite（runs.db）+ presets.json，每次计算落库，历史列表点击即回放"，原型 HTML 里也留了 `histBox` 占位但没有实现。现在补上：

- 表结构：`runs(id, ts, text, raw, slots, curves, status)`
- 每次 `/api/solve` 成功即落一条；`raw` 存用户原句（回放时合法性判定要用原句，不能用归一化文本）
- `GET /api/history?limit=20` 列表
- `POST /api/history/<id>/load` 回放：把该次 `slots` 还原成当前会话状态 → 重算 → 返回结果
- 前端左下列表显示「#编号 时间 · 型序列 · 关键参数」，点击即回放并重绘

回放不是"显示一张旧图"，而是**用当时的参数重新算一遍**——这样图上的悬停、点击断面、`/api/section` 全都可用。

## 五、调试中发现的两个问题

### 1. 「糙率改成0.02」解析不出来

规则层的连接词只认「为/是/=/:/取」，不认「改成/换成/改为」。逐条输入测试里，前 7 句全对，一到修改句就失败——表现和"模型失忆"一模一样，但根因是规则层。

修复：抽出一个统一的连接词常量，所有槽位复用：

```python
CONN = r"(?:为|是|=|:|取|改成|换成|改为|调到|调整到|调成|变为|变成)?"
```

### 2. B 类合法性被误判成 A 类

新服务端一开始把**归一化后的文本**同时喂给 adapter 和 legality。adapter 需要归一化文本（它按数字匹配水位/渠底高程），但 legality 需要**原句**——中文数字被转成阿拉伯数字之后，「五米宽」「千分之」这些 B 类特征就消失了。

修复：会话里同时保存 `texts`（归一化）和 `raws`（原句），adapter 用前者、legality 用后者。这个问题是回归测试（step11 的 B1 用例）抓出来的。

## 七、局限（写进报告时建议保留）

1. **会话状态在内存**：`server.py` 一重启，当前参数表清空（历史记录仍在库里）。要跨重启保留，把 `STATE["slots"]` 也落库即可。
2. **单会话**：目前一个进程一套状态，多标签页会互相覆盖。要支持多用户就加 `session_id`（顶层设计里本来就是这么设计的）。
3. **消息气泡不持久化**：回放的是"参数 + 结果"，不是当时的聊天记录。
4. **模型仍是无状态抽取器**：这是刻意设计，不是缺陷。
