## 四、按原文照抄会踩的坑（已修）

### 1. 合并层字符串比较 → 直接 500 崩溃【严重】

`merge.py` 原文：

```python
elif ... and abs(float(slots[k]) - float(v)) > 1e-9:
```

`section` 是字符串，规则给出 `trapezoidal`、模型也给出 `trapezoidal` 时，这句执行 `float("trapezoidal")`，抛 `ValueError`，被 `server.py` 兜成 500。

- 复现：验收第 2 条，`ValueError: could not convert string to float: 'trapezoidal'`
- 修复：数值字段才做差值比较，字符串字段用 `==`（`merge.py` 新增 `NUMERIC` 元组）

### 2. `边坡1比1.5` 被解析成 `m=1.0`

`parser.py` 的边坡正则里，第一条 `边坡(?:系数)?...NUM` 会先吃掉「边坡1」，导致梯形的边坡系数少算。而 `1比1.5` 才是真正的边坡系数 1.5。

- 复现：`m: 1.0`（错误）→ 若用于计算，过水断面会整套算错
- 修复：给第一条加负向先行断言 `(?!\s*[:比]\s*\d)`，让「1比1.5 / 1:1.5」交给第二条正则取后项
- 修复后：`m: 1.5` ✅

### 3. 「三百」「五百」不转换，导致渠长丢失

`normalize()` 只处理了「十、百、千」出现在 `分之` 里的情况，独立的「三百米」原样保留，`L` 的正则需要数字，于是漏掉。

- 复现：`missing: ["L"]`，`normalized` 里仍是「算三百米」
- 修复：在「十」之前增加一趟 `[零一二三四五六七八九两][百千][...]*` → `to_number()` 的替换
- 修复后：`略`→`算300米`，`L: 300.0` ✅

### 4. `底坡1/500` 会被解析成 `i=1.0`

原第二条正则 `1\s*/\s*(\d+)` 用 `group(1)`（分母）当坡度，且被第一条正则抢先匹配掉「底坡1」而根本轮不到。

- 修复：把 `1/n` 比值单独前置处理，`i = 1/denominator`
- 现状：`1/1000 → 0.001`、`1/500 → 0.002`、`1/200 → 0.005` ✅

### 5. 糙率兜底写在模型分支里 → 规则独解时失效【隐蔽】

原文把「糙率 ≥ 1 就除以 1000」的修正放在 `if missing and use_llm:` 内部。可规则解析器自己就会把「糙率十五」解析成 **15**；一旦其余字段齐全，`missing` 为空、根本不进模型分支，兜底永远不执行。

- 复现：验收第 6 条 `n: 15.0`（未修正）
- 修复：把修正移出模型分支，对任何来源的 n 生效
- 修复后：`n: 0.015` ✅

### 6. 修正后两条警告自相矛盾

规则层先报「糙率 15.000 超出合理范围」，兜底后又报「已按 0.0150 处理」，同一条输入两条警告互相打脸。

- 修复：应用兜底时先剔除基于原始值的那条范围警告
- 修复后：只剩「糙率 15.000 明显偏大，已按 0.0150 处理，请确认」✅

### 7. 变坡提示文案与实际行为不符

原文写「将交由模型处理」，但 `merge` 只在缺字段时才调模型，变坡场景并不会走模型。已改为「本版仅支持单段渠道，请确认或拆分后再算」。

## 五、qwen3:4b-nothink 调试实录

### 第 1 轮：原始提示词，两类稳定复现的错误

用 6 条句子压测模型通道，发现：

| 用例 | 期望 | 模型实得 | 性质 |
|---|---|---|---|
| 五米宽梯形渠…**糙率十五**…算三百米 | n = 0.015 | **n = 0.15** | 差 10 倍（比 15 好，但仍错） |
| 梯形渠道…**渠末正常水深**，渠长1.2公里 | h0 = 未知 | **h0 = 1.2** | 凭空编造，把渠长的 1.2 抄给了控制水深 |

第一条尤其危险：`merge.py` 的兜底只拦「n ≥ 1」，`0.15` 拦不住。若规则通道恰好漏了糙率，这个 10 倍误差会**静默进入计算内核**。

### 第 2 轮：改提示词

针对两类错误在 `SYSTEM` 里补了 4 条硬规则 + 2 个反例（正好是失败的那两句）：

- 规则 8：糙率**只有中文数字口述时**才按工程量级换算（十五→0.015、二十→0.020）
- 规则 9：**「渠末正常水深」只是边界条件**，h0 必须填 -1，不许把渠长数字抄给 h0
- 规则 10：中文大数换算（三百=300、一千二=1200、五百=500）
- 规则 11：一句里出现两个宽度时以「底宽」为准

### 第 3 轮：发现自己引入了过修正

改完后 B、E 都对，但新用例暴露副作用：

> 「矩形渠…**糙率0.3**…」→ 模型输出 **n = 0.03**

规则 8 里「按工程常数量级改写」写得过宽，模型把显式给出的 0.3 也压了一个量级。**这是提示词改动引入的回归**，不是原模型的问题。

### 第 4 轮：收紧后定稿

把规则 8 改成「只有中文数字口述才换算；阿拉伯数字原样输出，绝不能改数量级」，再跑：

| 用例 | 结果 |
|---|---|
| A 文档示例句 | 8/8 正确 |
| B 糙率十五 + 三百米 | n=0.015、L=300 ✅ |
| C 帮我算个水面线 | 全部 -1，未编造 ✅ |
| D 糙率0.3 + 百分之五 | n=0.3 保持、i=0.05 ✅ |
| E 渠末正常水深 + 1.2公里 | h0=-1、L=1200 ✅ |
| F 1/1000 + 0.5个方 | i=0.001、Q=0.5 ✅ |

**6/6 通过。**

## 七、残留风险（诚实记录）

1. **模型会抄邻近数值**。压测里输入「糙率0.3，底宽5米，糙率0.3」（一句里没有流量）时，模型把 Q 也填成了 0.3。信息残缺的句子仍可能被"脑补"，建议内核前加一道量纲/范围校验（比如 Q>0、n∈[0.008, 0.3]、i∈(0, 0.1]）。
2. **「一千二」这类省略读法**目前会算成 1002。工程文档里一般写「一千二百」，暂不处理；真遇到就在 `to_number` 里补尾数规则。
3. **规则正则仍是白名单**。文档自己也说了：解析不出的句子记到 `examples.txt`，再补正则。目前 `examples.txt` 还没有，建议把现场遇到的失败句都攒进去。
4. **上下文只有 2048**。`llm.py` 里 `num_ctx=2048`，长描述会被截断；若要支持整段需求书，需要调大同时接受显存/内存代价。
5. **纯 CPU 推理**。14 tokens/s，一次抽取 7 秒左右。文档设计（规则优先）已经规避了大部分等待，但连续追问时体验仍受限于此。
